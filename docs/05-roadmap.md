# 演进路线（分阶段落地）

本文档用于描述从"快速落地"到"按业务域演进"的建议路径，避免一开始拆得过细。

---

## 阶段划分

### 阶段 1：MVP 骨架（当前阶段）✅

**目标**：建立基础架构和核心服务骨架

**已完成：**

- 1 个 API 网关（`gateway`）
- 3 个 BFF 应用（`ma-web`、`ma-admin`、`ma-mobile`）
- 3 个核心微服务（`ms-auth`、`ms-rbac`、`ms-user`）
- 统一配置管理（pnpm catalog + 根目录配置文件）
- 共享库基础结构（`servers/libs/shared`）

**待完善：**

- 各应用的业务逻辑实现
- 数据库设计与 ORM 集成
- 认证与权限校验流程
- 统一日志和监控

### 阶段 2：业务能力落地

**目标**：实现核心业务功能

**计划添加：**

- 完善认证流程（登录、token 刷新、会话管理）
- 实现 RBAC 权限系统（角色、权限、策略）
- 用户管理功能（注册、资料、权限分配）
- 统一错误处理和响应格式
- API 文档生成（Swagger/OpenAPI）

### 阶段 3：按需扩展微服务

**时机**：当发布/性能/团队协作出现瓶颈时

**可考虑拆分：**

- `ms-order`：订单域（订单、支付、发货）
- `ms-product`：商品域（商品、分类、库存）
- `ms-notification`：通知服务（邮件、短信、站内信）
- `ms-file`：文件服务（上传、存储、CDN）
- `ms-analytics`：数据分析（埋点、统计、报表）

### 阶段 4：优化与治理

**目标**：提升系统可维护性和稳定性

**计划完善：**

- 服务间通信优化（可选 gRPC / 消息队列）
- 分布式追踪（OpenTelemetry）
- 性能监控和告警
- 自动化测试覆盖（单元测试 + E2E 测试）
- CI/CD 流程完善
- Docker 容器化和 K8s 部署

---

## 原则

1. **先垂直后水平**：优先按业务域拆分（订单、商品），而非技术职能（通知、文件）
2. **避免过早拆分**：2-4 个核心服务足以支撑 MVP，过早拆分增加复杂度
3. **保持边界清晰**：每个微服务只负责自己的数据和业务规则
4. **渐进式演进**：根据实际瓶颈决定何时拆分，而非预先设计
